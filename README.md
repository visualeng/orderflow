# orderflow

[![tests](https://github.com/visualeng/orderflow/actions/workflows/tests.yml/badge.svg)](https://github.com/visualeng/orderflow/actions/workflows/tests.yml)

Сервис заказов и складских остатков на Java 21 и Spring Boot 4: заводим
товары, кладём их на склад, забираем заказами. Учебный проект про то, чего
не было в предыдущих, — **транзакции, блокировки и идемпотентность** под
нагрузкой: что происходит, когда два заказа одновременно хотят один и тот
же товар.

## Как это работает

```
POST /api/orders (Idempotency-Key)
        │
        │ 1. занимаем ключ: INSERT в orders (UNIQUE на idempotency_key)
        │ 2. SELECT ... FOR UPDATE ORDER BY sku — берём товары под блокировку
        │ 3. проверяем остатки, списываем, сохраняем позиции
        │ 4. считаем total из позиций, а не берём от клиента
        ▼
  [ NEW ] ──confirm──► [ CONFIRMED ] ──ship──► [ SHIPPED ]
    │                      │
    └─────────cancel───────┴────► [ CANCELLED ]  товар вернулся на склад
```

Всё это одна транзакция: если не хватило товара, не откатывается ничего —
ни списание, ни сам заказ.

### Конкуренция за остаток

Остаток меняют две транзакции сразу, поэтому одного `@Version` мало: он
узнаёт о конфликте уже после того, как оба потока прочитали старое
значение, и часть из них всё равно придётся повторять. Здесь товар
берётся под пессимистическую блокировку — `SELECT ... FOR UPDATE` — и
остаток меняется, пока строка заблокирована.

Блокировки всегда идут в одном порядке (по `sku`, одним запросом), поэтому
два заказа с пересекающимися позициями не встают в тупик. Это не теория:
в тестах шесть параллельных заказов с разным составом проходят без
дедлоков.

### Идемпотентность

Каждый `POST /api/orders` обязан нести `Idempotency-Key`. Повтор с тем же
ключом возвращает тот же заказ (200 вместо 201) и **не списывает товар
второй раз** — это и проверяет тест на шесть параллельных запросов с
одинаковым ключом.

Ключ сравнивается не по телу, а по хешу канона: позиции сливаются по
повторяющимся SKU и сортируются. Поэтому «клавиатура 2, мышь 1» и
«мышь 1, клавиатура 2» — один и тот же заказ, а вот «клавиатура 2» под тем
же ключом — уже 409.

Сам ключ защищает база: `idempotency_key` объявлен `UNIQUE`, и запись
заказа происходит **до** списания остатков. Параллельный повтор упрётся в
уникальный индекс, его транзакция откатится, и клиент получит уже
существующий заказ вместо ошибки.

### Жизненный цикл

| Переход                    | Кто инициирует            | Если статус не тот                          |
|----------------------------|----------------------------|---------------------------------------------|
| `NEW → CONFIRMED`          | `POST /api/orders/{id}/confirm` | 409 `invalid_transition`                |
| `CONFIRMED → SHIPPED`      | `POST /api/orders/{id}/ship`    | 409 `invalid_transition`                |
| `NEW`/`CONFIRMED` → `CANCELLED` | `POST /api/orders/{id}/cancel` | 409 `invalid_transition`; остаток возвращается |

`SHIPPED` и `CANCELLED` — финальные: отменять отгруженный заказ нельзя.

## API

Товар и заказ:

```console
$ curl -X POST localhost:8080/api/products \
    -H "Content-Type: application/json" -d @product.json
{"sku":"kb-1","name":"клавиатура","priceCents":49900,"qty":5,"createdAt":"...","updatedAt":"..."}

$ curl -X POST localhost:8080/api/orders \
    -H "Content-Type: application/json" \
    -H "Idempotency-Key: order-777" -d @order.json
{"id":"20018c8f-e834-4f05-8dc1-386e3c383ade","status":"NEW","totalCents":102300,
 "items":[{"sku":"kb-1","qty":2,"priceCents":49900},{"sku":"mouse-1","qty":1,"priceCents":2500}],...}
```

Повтор того же ключа с тем же составом — тот же заказ и 200:

```console
$ curl -X POST localhost:8080/api/orders -H "Idempotency-Key: order-777" -d @order.json
{"id":"20018c8f-e834-4f05-8dc1-386e3c383ade","status":"NEW","totalCents":102300,...}
```

Тот же ключ с другим составом — 409, и ничего не списано:

```console
HTTP 409
{"status":409,"code":"idempotency_key_reused","detail":"этот Idempotency-Key уже использовали с другим составом заказа",...}
```

Не хватило товара — 409 с остатком в ответе, чтобы клиенту не пришлось
угадывать:

```console
HTTP 409
{"status":409,"code":"insufficient_stock","sku":"kb-1","available":3,"requested":99,
 "detail":"по товару kb-1 осталось 3, просят 99",...}
```

Жизненный цикл и отмена с возвратом на склад:

```console
$ curl -X POST localhost:8080/api/orders/20018c8f-.../confirm   # CONFIRMED
$ curl -X POST localhost:8080/api/orders/20018c8f-.../ship       # SHIPPED
$ curl -X POST localhost:8080/api/orders/20018c8f-.../cancel    # 409 invalid_transition
```

Список с фильтром и пагинацией:

```console
$ curl "localhost:8080/api/orders?status=SHIPPED&size=5"
{"items":[...],"total":1,"page":1,"size":5}
```

Ошибки всегда в одном формате (RFC 7807 `ProblemDetail` плюс свой `code`):
400 без ключа или мимо валидации, 404 неизвестный товар или заказ,
409 нехватка остатка, недопустимый переход и переиспользование ключа.

## Схема данных

```
products        sku PK, name, price_cents, qty, version (оптимистичная блокировка)
orders          id PK, idempotency_key UNIQUE, request_hash, status, total_cents
order_items     (order_id, sku) PK, qty, price_cents — цена на момент заказа
```

Цена позиции сохраняется при создании заказа: правка прайса в каталоге не
переписывает историю уже оформленных заказов (это тоже проверяется тестом).
Индексы — на `orders(status, created_at)` под фильтр списка и на
`order_items(sku)`. Схемой владеет Flyway, Hibernate только проверяет, что
она совпадает (`ddl-auto: validate`).

## Как запустить

Нужен Java 21+ и postgres 17+:

```console
$ createdb orderflow

$ export DATABASE_URL="jdbc:postgresql://localhost:5432/orderflow"
$ export DATABASE_USER=postgres
$ export DATABASE_PASSWORD="пароль"
$ ./mvnw spring-boot:run
```

Переменные окружения:

| Переменная          | По умолчанию   | Что это                          |
|---------------------|----------------|-----------------------------------|
| `DATABASE_URL`      | — (обязательно) | JDBC DSN postgres               |
| `DATABASE_USER`     | `postgres`     | пользователь БД                  |
| `DATABASE_PASSWORD` | `postgres`     | пароль                           |
| `PORT`              | `8080`         | порт                             |

Логин и пароль задаются отдельными переменными, а не внутри DSN: драйвер
postgres не разбирает `user:pass@` в JDBC URL и принимает их за часть
имени хоста (проверено на локальном прогоне и на CI).

## Тесты

```console
$ export TEST_DATABASE_URL="jdbc:postgresql://localhost:5432/orderflow_test"
$ export TEST_DATABASE_USER=postgres
$ export TEST_DATABASE_PASSWORD="пароль"
$ ./mvnw test
...
[INFO] Tests run: 34, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

Что проверяется:

- **конкуренция**: десять параллельных заказов на остаток 5 дают ровно
  пять 201 и пять 409, а на складе ноль — «списать больше, чем есть» не
 возможно; шесть параллельных заказов с пересекающимися позициями проходят
  без дедлоков;
- **идемпотентность**: повтор ключа не списывает товар второй раз; тот же
  ключ с другим составом — 409; шесть параллельных запросов с одним ключом
  создают ровно один заказ;
- **остатки**: нехватка возвращает 409 с остатком и не создаёт заказ;
  отмена возвращает товар; повторная отмена и отмена отгруженного — 409;
- **жизненный цикл**: подтверждение, отгрузка, запрет недопустимых переходов;
- **снимок цены**: правка прайса не меняет уже оформленный заказ;
- **нормализация позиций** (юнит-тест без базы): слияние дублей по SKU,
  сортировка, независимость хеша от порядка позиций, защита от переполнения.

Тесты идут через настоящий HTTP (MockMvc) и настоящий postgres: моки
конкуренции тут ничего не проверяли бы. Таблицы очищаются перед каждым
тестом, схему накатывает Flyway. Без `TEST_DATABASE_URL` интеграционные
тесты пропускаются, юнит-тесты идут всегда — на CI переменная задана.

## Docker

```console
$ docker compose up --build
```

Поднимает postgres и приложение одной командой: база создастся, миграции
применятся, сервер будет на `localhost:8080`. На CI этот же compose
собирается и проверяется живым healthz — образ не «просто собрался», он
реально стартует.

## Как устроено

```
dev.orderflow.product    товар и склад: сущность, репозиторий, сервис, REST
dev.orderflow.order      заказ: сущность, позиции, статусы, REST
dev.orderflow.order      OrderWriter — создание в одной транзакции
dev.orderflow.order      OrderItems — канон позиций и хеш запроса
dev.orderflow.common     ошибки в формате ProblemDetail
```

`OrderWriter` выделен отдельно не для красоты: `@Transactional` работает
только через прокси, а `OrderService` ловит нарушение уникального ключа
уже вне транзакции, чтобы отдать клиенту существующий заказ вместо ошибки.
